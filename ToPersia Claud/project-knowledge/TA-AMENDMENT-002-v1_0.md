# ToPersia — Architecture Amendment 002
## اصلاح دو خطای تصمیم: رندر کلاسیک وردپرس (نه Astro) + قالب Woodmart (نه JNews)
### شواهد: JetEngine Elementor docs · wpml.org/theme/yootheme · Jegtheme JNews docs · xtemos Woodmart docs (۲۰۲۶-۰۷-۱۴)

---

## ۰. اقرار صریح

در تصمیم قبلی («وردپرس/جت‌انجین/قالب») این فرض را **صریحاً نوشتم و پرسیدم**: «معماری Headless+Astro را دست‌نخورده در نظر می‌گیرم... اگر منظورتان وردپرس کلاسیک زنده بود، بگویید» — تصحیحی نیامد و کار با آن فرض تا TA-FINAL و چند ممیزی ادامه یافت. این توضیح چرایی است، نه توجیه. مالک اکنون صریحاً گفته: front و back هر دو وردپرس، بدون Astro/JS، با یکی از سه قالب موجود. **هر دو خطا (فرض رندر + انتخاب قالب JNews) اینجا کامل اصلاح می‌شود.**

---

## ۱. اصلاح ۱ — معماری رندر: کلاسیک، نه Headless

**یافته فنی پیش از تصمیم:** JetEngine داده را همیشه از طریق **ویجت‌های Elementor** (Listing Grid، Dynamic Field) رندر می‌کند، نه بیلدر خودِ قالب و نه یک لایه جداگانه JS. یعنی معماری صحیح: **وردپرس (JetEngine+WPML) + Elementor برای ساخت قالب Single/Archive هر Custom Post Type + قالب پایه برای چارچوب/چیدمان کلی.** بدون Astro، بدون REST API جداگانه برای Build، بدون لایه JS مستقل.

**پیامد مستقیم روی ریسک Fan-in:** توجیه اصلی Astro (خنثی‌سازی کامل فشار C13/P6/P5 در لحظه درخواست) دیگر با SSG تضمین نمی‌شود. باید صادق بود: **کش صفحه کامل + CDN، تضمینی به قدرت فایل استاتیک نیست.** با SSG هرگز کوئری زنده‌ای برای این صفحات رخ نمی‌داد؛ با کش، لحظه cache-miss (بعد از انتشار/ویرایش محتوا، یا انقضای TTL) یک رندر زنده واقعی به دیتابیس تحمیل می‌کند. این ریسک قابل‌مدیریت است (TTL بلند + Purge هدفمند فقط صفحات متأثر + پیش‌گرم‌سازی کش پس از هر بچ)، اما ضعیف‌تر از تضمین SSG است — نه معادلش.

**الزامات بازنویسی‌شده:**
| شناسه | قبل (Astro) | بعد (کلاسیک+کش) |
|--------|--------------|-------------------|
| NFR-OPS-01 | خروجی استاتیک بچ روزانه | صفحه‌سازی زنده + **کش کامل صفحه** (LiteSpeed Cache/WP Rocket بسته به هاست) با TTL بلند |
| NFR-OPS-02 | جداسازی فیزیکی Author/Serve | جداسازی منطقی: کش لبه (CDN) جلوی درخواست کاربر می‌نشیند؛ WordPress فقط در cache-miss درگیر می‌شود |
| HF2 | SSG PASS مطلق | PASS **مشروط به پیکربندی صحیح کش** — نیازمند پایلوت جدید (بخش ۳) |

## ۲. اصلاح ۲ — قالب: Woodmart، نه JNews

جدول شواهد بالای پیام. **دلیل حذف JNews:** توصیه رسمی خودِ سازنده به استفاده از Polylang به‌جای WPML، دقیقاً در تضاد با ستون فقرات چندزبانگی این پروژه (WPML، به‌خاطر شراکت رسمی با JetEngine). **دلیل حذف قطعی YOOtheme:** wpml.org مستقیماً «در حال حاضر سازگار نیست» اعلام کرده — این مبهم نیست، یک بلاک مستند و حل‌نشده است. **دلیل انتخاب Woodmart:** تنها گزینه بدون مشکل شناخته‌شده WPML + سازگاری کامل و عمیق Elementor + مهندسی‌شده برای عملکرد (که حالا در رندر زنده اهمیت مستقیم دارد، برخلاف فرض قبلی «قالب بی‌اهمیت است»).

**اقدام احتیاطی برای فاز ۵ (نه مسدودکننده):** Woodmart بر پایه WooCommerce طراحی شده؛ باید تأیید شود فعال‌سازی WooCommerce اجباری نیست یا در صورت لزوم، غیرفعال نگه داشته شود تا سطح مواجهه (attack surface) و منوهای بی‌ربط اضافه نشود.

---

## ۳. پایلوت جدید — P2″ (جایگزین ارزش اثباتی P2-alpha)

P2-alpha (بنچمارک Astro) دیگر معماری فعال را اعتبارسنجی نمی‌کند و به‌عنوان شاهد تاریخی می‌ماند، نه اعتبار جاری. پایلوت جدید لازم:

**P2″ — آزمون کش/CDN روی صفحه Hub شبیه‌سازی‌شده:** یک Custom Post Type آزمایشی با ۳۰۰+ آیتم و رابطه (شبیه‌سازی C13)؛ نصب افزونه کش سازگار با هاست (LiteSpeed Cache اگر هاست LiteSpeed باشد، وگرنه WP Rocket/WP Super Cache)؛ اندازه‌گیری TTFB در دو حالت: **Cache Warm** (باید <۲۰۰ms باشد) و **Cache Cold/Miss** (زمان واقعی رندر زنده JetEngine روی ۳۰۰+ رابطه — این عدد باید ثبت و ارزیابی شود، نه فرض). معیار قبول: Warm در آستانه هدف؛ Cold در محدوده قابل‌تحمل تجربه کاربر (<۳ ثانیه) روی هاست فعلی.
