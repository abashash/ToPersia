## ۱. مدل داده منطقی (LDM) — نُه لایه، مستقل از فناوری

**L1 — هسته موجودیت:** هر نمونه یک رکورد با `entity_id` پایدار و تغییرناپذیر (مرجع همه یال‌ها، ترجمه‌ها و JSON-LD @id)، `entity_type` (یکی از ۴۲ + D1–D6)، وضعیت انتشار (پیش‌نویس/منتشر/گراف‌فقط)، و مهر نسخه/تاریخ. شناسه از URL مستقل است (تصمیم ساختار URL: فاز پیاده‌سازی).

**L2 — سیستم نوع-فیلد:** ۶۹۷ فیلد مصوب طبق طبقه‌بندی ده‌کلاسه TA-I18N-D001. قاعده اجرایی: کلاس هر فیلد در تعریف Schema سیستم قفل می‌شود و تعیین‌کننده رفتار ذخیره/ترجمه/رندر است — نه قضاوت موردی ادیتور. این همان دیوار ضد-Drift ریسک ۱ Handover در سطح پیاده‌سازی است.

**L3 — رکورد رابطه (Edge-Record):** هر یال از ۲۳ رابطه ذخیره‌شونده یک رکورد مستقل: `{rel_type, src_id, dst_id, props, props_i18n}`. کاردینالیته‌ها و دامنه Source/Target عیناً از IA به‌صورت قواعد اعتبارسنجی سخت اجرا می‌شوند. **الزام غیرقابل‌مذاکره:** پشتیبانی از صفت روی یال شامل صفت زبان‌وابسته (`venue_name` در R16، متادیتای R20، `sequence_order` در R03) — بدون ساخت Node میانی (نقض P-10/C6).

**L4 — لایه مشتق (Build-Time، هرگز منبع):** R02/R21 (معکوس R01/R20)، مسیر مادی‌شده Breadcrumb، جغرافیای Derived قوم (CA-C-D010)، بخش Designations شهر، شمارنده‌های دروازه انتشار C13، و نمای اتحاد R13∪R14 (بخش ۲). بازتولید کامل در هر بچ روزانه؛ ذخیره فقط به‌عنوان کش انتشار.

**L5 — لایه i18n:** جدول ترجمه با کلید `(entity_id | edge_id, field_key, lang)` برای کلاس‌های TEXT/SEO/NAME/اجزای Hybrid؛ **واژه‌نامه مرکزی** برای لیبل ۷۰ Classification + ~۲۸ Enum + Boolean (F004)؛ خانواده نام ۹زبانه جایگزین تعمیم‌ناپذیر جفت fa/en (F001)؛ slug زبان‌محور به‌عنوان فیلد فنی (F006). زبان‌های غایب: fallback زنجیره‌ای EN→FA با برچسب «بازبینی‌نشده» (NFR-CAP-04).

**L6 — قرارداد Content Layer به‌مثابه Value-Object:** ارجاع فاقد رابطه IA = شیء مقداری `{label_i18n, url?}` درون فیلد؛ **نه edge، نه entity**. قاعده V-CL-01: هیچ مسیر خودکاری برای تبدیل CL به رابطه وجود ندارد؛ V-CL-02: به‌سوی Category P فقط R22/R23/R24 مجاز است (الگوی خطای پرتکرار فاز ۳ — اکنون قاعده ماشینی).

**L7 — لایه Volatility (اجرای DP-402):** فیلدهای حامل مقدار فرار ممنوع؛ `last_verified_date` + `official_source_link` در قالب و JSON-LD صفحات P1/P2 الزامی؛ خط هشدار خودکار ماهانه + SLA ≤۷۲ ساعت؛ چرخه سالانه P6 پیش از مناسبت‌های قمری.

**L8 — لایه رسانه:** رکورد رسانه = فایل + متادیتای per-lang (alt/caption از الگو/واژه‌نامه، نه ترجمه آزاد — F003) + خط بهینه‌سازی خودکار در انتشار؛ سیاست اصالت F-OPS-21 (AI فقط مفهومی/برچسب‌دار؛ Hero مکان واقعی = عکس اصیل).

**L9 — لایه انتشار:** جداسازی کامل Author/Serve (NFR-OPS-02)؛ بچ روزانه: بازساخت مشتقات L4 → تولید HTML×زبان + JSON-LD×زبان + sitemap×زبان؛ خروجی استاتیک CDN-محور (NFR-INFRA-01)؛ Export کامل داده در قالب باز در هر بچ (NFR-STRAT-02 — پادزهر Vendor-Lock با قید صفر-مهاجرت).

## ۲. حکم R13/R14 — رفع ریسک «داده تکراری/ناسازگار» بدون دست‌زدن به Freeze

**صورت مسئله (Handover §4):** واقعیت «حافظ در آرامگاه حافظ مدفون است» را می‌توان دوجا رمزگذاری کرد: R14-BURIED_IN (C12→A2) و R13-ASSOCIATED_WITH_FIGURE (A2→C12) — ریسک ذخیره دوگانه و واگرایی.

**حکم (TA-REQ-D001):**
1. هر دو رابطه **در جهت مصوب IA خود** ذخیره می‌شوند — هیچ تغییری در تعاریف Frozen.
2. **تقدم واقعیت‌نگاری:** سه واقعیت زیستی (تولد/وفات/دفن) منحصراً در R14 ذخیره می‌شوند (SSOT = سمت C12، سازگار با کاردینالیته Many-to-One per type).
3. **قاعده اعتبارسنجی V-R13-01:** ثبت یال R13 بین جفتی که همان واقعیت را R14 پوشش داده، رد می‌شود (R13 برای پیوندهای معنایی ورای سه واقعیت زیستی است: «شاه‌عباس ↔ میدان نقش‌جهان»).
4. **رندر اتحادی (L4):** بخش «شخصیت‌های تاریخی» هر صفحه = union(معکوس R14، معکوس R13) با برچسب نوع پیوند از `rel_subtype`/نوع رابطه — بدون یال اضافه.

نتیجه: صفر تکرار، صفر ناسازگاری، صفر تغییر IA. یادداشت «Future IA Review» لاگ v1.2 سر جای خود می‌ماند (ادغام احتمالی آینده، تصمیم مالک)، اما مانع پیاده‌سازی نیست.

## ۳. سیاست انتشار Nodeهای گراف‌فقط (TA-REQ-D002 — رفع پرچم GEO در TA-VOL §۴.۷)

Nodeهای گراف‌فقط (G7 گروه ۳، اکثر G4) **URL مستقل نمی‌گیرند** (ضد Thin-Content) اما **از دید ماشین پنهان نمی‌مانند:** در JSON-LD صفحات والد/مرتبط به‌صورت موجودیت تودرتو با `@id` پایدار ظاهر می‌شوند (مثلاً روستای فاقد صفحه، در `containsPlace`/`location` صفحه شهرستان یا جاذبه). لنگر GEO حفظ، هزینه صفحه صفر.

## ۴. نمونه‌سازی Schema.org — سه مورد سخت (استخراج الزام، نه نگاشت کامل)

### ۴.۱ — A2 با R20 دارای‌شرایط (الگوی «تخت‌جمشید ← D1»)
```json
{ "@type": "LandmarksOrHistoricalBuildings", "@id": "https://…/e/a2-persepolis",
  "name": "Persepolis", "inLanguage": "en",
  "containedInPlace": { "@id": "…/e/g4-marvdasht" },
  "award": "UNESCO World Heritage Site (1979)",
  "additionalProperty": [
    { "@type": "PropertyValue", "name": "unesco_criteria", "value": "i, iii, vi" },
    { "@type": "PropertyValue", "name": "designation_status", "value": "inscribed" } ],
  "sameAs": [ "https://whc.unesco.org/en/list/114", "https://www.wikidata.org/wiki/Q129072" ],
  "temporalCoverage": { "@id": "…/e/c13-achaemenid" } }
```
→ متادیتای یال R20 به `award` + آرایه `additionalProperty` سریال می‌شود؛ هیچ Node میانی ساخته نمی‌شود (P-10 ✓).

### ۴.۲ — P9 با صفتِ یالِ ترتیب (الگوی مسیر)
```json
{ "@type": "TouristTrip", "@id": "…/e/p9-silkroad-ir", "name": "…",
  "itinerary": { "@type": "ItemList", "itemListOrder": "Ordered",
    "itemListElement": [
      { "@type": "ListItem", "position": 1, "item": { "@id": "…/e/g5-tabriz" } },
      { "@type": "ListItem", "position": 2, "item": { "@id": "…/e/g5-zanjan" } } ] } }
```
→ `sequence_order` (صفت روی R03) مستقیماً به `position` نگاشت می‌شود — اثبات این‌که صفت یال باید در لایه داده first-class باشد (HF8).

### ۴.۳ — C10 فرامرزی با R27 (الگوی «نوروز») — عیناً Baseline فریزشده CA-C
```json
{ "@type": "Event", "@id": "…/e/c10-nowruz", "name": "Nowruz", "inLanguage": "en",
  "eventSchedule": { "@type": "Schedule", "repeatFrequency": "P1Y" },
  "location": [ { "@type": "Country", "name": "Iran" }, { "@type": "Country", "name": "…" } ],
  "sameAs": [ "https://ich.unesco.org/en/RL/nowruz-01161", "https://www.wikidata.org/wiki/Q129983" ],
  "subEvent": { "@id": "…/e/e1-nowruz-celebration-1405-shiraz" } }
```
→ مطابق خط فریزشده C10: `@type: Event + eventSchedule (P1Y) + sameAs (R27 URIs + UNESCO URL)`. تمایز معماری C10 (سنت) از E1 (برگزاری تاریخ‌دار) در Markup با الگوی استاندارد `subEvent`/`superEvent` حفظ می‌شود — E1 با `superEvent` به C10 اشاره می‌کند. غنی‌سازی افزودنیِ مجاز (بدون تغییر @type): `additionalType` به کلاس Wikidata. **نکته ثبت‌شده برای ۴.۸:** فقدان نوع بومی ICH در Schema.org را خودِ Baseline مصوب با sameAs به UNESCO-ICH جبران کرده است — R27 دقیقاً همین نقش را دارد.

**الزامات استخراج‌شده:** REQ-SCH-01 تولید JSON-LD تودرتو با @id ارجاعی per-entity · REQ-SCH-02 سریال‌سازی صفت یال به ساختارهای استاندارد (position/award/additionalProperty) · REQ-SCH-03 تولید per-lang از L5 · REQ-SCH-04 تزریق sameAs/External URI (R27، Wikidata) · REQ-SCH-05 تزریق last_verified_date به‌عنوان dateModified در P1/P2/P6.
