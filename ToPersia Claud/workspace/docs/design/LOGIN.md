### ۱-ث آیا وردپرس به `…@users.topersia.com` نامه می‌فرستد؟

- **در کد ما: نه.** در `plugin/` هیچ فراخوانی `wp_mail`/`mail(` نیست (grep ۱۹ اکتبر روی `topersia-user-core`، `topersia-core`، `topersia-ai-summarizer`). `wp_create_user` نامه نمی‌فرستد. مهاجرت P5-D354 صراحتاً `send_email_change_email` را خاموش می‌کند (`privacy.php:273`) تا نامهٔ «ایمیل عوض شد» به ایمیل ساختگی نرود.
- **در هستهٔ وردپرس: چند مسیر ممکن است** [استنباط از رفتار هستهٔ وردپرس؛ روی زنده آزموده نشده]: ① `wp-login.php?action=lostpassword` با نام ورود حساب (نام ورود تصادفی و ناشناخته است، ولی مدیر می‌بیند) ② تغییر ایمیل/گذرواژه از پیشخوان توسط مدیر ③ درخواست برون‌بری/پاک‌سازی داده (ابزار حریم خصوصی وردپرس) ④ اعلان نظر/دیدگاه به نویسنده (مشترک پست ندارد) ⑤ افزونه‌های دیگر (JetReviews، Rank Math، WPML، المنتور) که برای هر کاربر نامه بفرستند.
- **اثر:** هر نامه به دامنهٔ بی‌صندوق = bounce. نرخ bounce بالا اعتبار دامنه/IP فرستنده را خراب می‌کند و بعد **نامهٔ کد ورود هم به اسپم می‌رود** — دقیقاً خطر طراحی حاضر. هاست: `mail()` غیرفعال است (`UC/CLAUDE.md` بند «هر فراخوانی بیرونی»؛ سنجش زنده در `LQ-USER`، `CURRENT.md`)، پس امروز نامه‌ای **اصلاً** نمی‌رود؛ خطر وقتی واقعی می‌شود که SMTP راه بیفتد.
- **پیشنهاد [پیشنهاد]:** پیش از روشن‌کردن هر ارسال، صافی `wp_mail` / `pre_wp_mail` که نامه‌ای را که گیرنده‌اش در دامنهٔ `users.topersia.com` (`ToPersia_Privacy::synthetic_email`) است **بی‌صدا حذف** کند و در لاگ فقط شمار بنویسد؛ و `allow_password_reset` را برای مشترک‌ها `false` کند (§۲-ث). دامنهٔ ساختگی هم: رکورد **Null MX** (RFC 7505: `MX 0 .`) و `SPF -all` — [تأییدنشده] که اکنون MX دارد یا ندارد؛ مالک در DNS ببیند.

## ۲ — مدل هویت

### ۲-الف اصل‌ها

۱. **یک حساب = یک `user_id`** با **حداکثر دو شناسهٔ تأییدشده**: موبایل ایران (`^09\d{9}$`) و ایمیل. دست‌کم یکی لازم است.
۲. **یکتایی:** هر شناسه فقط به یک حساب. ایمیل: `email_exists()` وردپرس (ستون `user_email` شاخص دارد). موبایل: امروز فقط قرارداد کد است؛ **قفل** پیش از ساخت/پیوند لازم است (§۱-ت).
۳. **شناسهٔ دوم فقط پس از ورود و تأیید** (کد به همان شناسهٔ تازه). هیچ ادغام خودکار نیست؛ حتی اگر ایمیلی که کاربر در حساب موبایلی وارد می‌کند با حساب ایمیلی دیگری یکی باشد.
۴. شماره/ایمیل **هرگز** در `display_name`/`nicename`/`login`/نظر/REST/نقشهٔ سایت (P5-D354) و **هرگز در لاگ** (§۷).
۵. **حساب‌های دارای دسترسی** (`manage_options · edit_posts · edit_pages · upload_files`) از هر دو کانال کد رد می‌شوند — همان `may_use_otp()` (`auth.php:331-339`). ایمیل کد، گذرواژهٔ مدیر را جایگزین نمی‌کند.

### ۲-پ پیوند شناسهٔ دوم (فقط واردشده)

`topersia_link_email_send` (نیازمند ورود + نانس + سقف‌ها) ← کد به ایمیل تازه ← `topersia_link_email_verify` ← در موفقیت: `wp_update_user(['ID'=>…, 'user_email'=>$email])` با `send_email_change_email` موقتاً خاموش و **نامهٔ اعلان امنیتی به ایمیل پیشین فقط اگر واقعی بود** (ساختگی نه). همین برای «افزودن موبایل به حساب ایمیلی» با Mediana و `_topersia_mobile`؛ پیش از نوشتن، یکتایی شماره و قفل.
حساب ایمیلی (بی موبایل): ایمیل واقعی در `user_email`، `_topersia_mobile` نیست؛ نام ورود/نامک/نام نمایشی همان تصادفی/خنثی (`create_user` تعمیم‌یافته، §۱۰).

### ۲-ت برخورد — ایمیل متعلق به حساب دیگر

| وضعیت | رفتار |
|---|---|
| ورود با ایمیل X، حسابی با X هست | ورود به همان حساب (پس از کد) |
| ورود با ایمیل X، حساب نیست | حساب تازهٔ ایمیلی پس از کد (ثبت‌نام = ورود، مثل موبایل) |
| واردشده در حساب A می‌خواهد X را پیوند بدهد و X مال B است | **ادغام نه، خطای افشاگر نه.** به UI همان پاسخ همیشگی «اگر آدرس معتبر باشد کدی فرستاده شد». به X (صاحب B) نامهٔ «کسی خواست این نشانی را به حساب دیگری وصل کند؛ اگر شما بودید با همین ایمیل وارد شوید و از آنجا شمارهٔ خود را تغییر دهید؛ وگرنه نادیده بگیرید» می‌رود. هیچ کدی ساخته نمی‌شود و تأیید هرگز موفق نمی‌شود |

### ۲-ث بازیابی وقتی یکی از دست رفت

- **موبایل رفته، ایمیل هست:** ورود با ایمیل ← «تغییر موبایل» با کد پیامکی به شمارهٔ **تازه** ← `_topersia_mobile` عوض می‌شود + اعلان به ایمیل. شمارهٔ قدیمی آزاد می‌شود (ممکن است اپراتور به دیگری بدهد؛ همین دلیل «نباید شماره تنها شناسهٔ حساب با داده حساس باشد» است).
- **ایمیل رفته، موبایل هست:** ورود با موبایل ← تغییر ایمیل با کد به نشانی تازه.
- **هر دو رفته:** خودکار نه؛ مسیر پشتیبانی (پرسش باز ۴).
- **قاعده‌ها [پیشنهاد]:** نمی‌توان **آخرین** شناسهٔ تأییدشده را حذف کرد؛ تغییر هر شناسه کد به شناسهٔ تازه + اعلان به شناسهٔ دیگر؛ فاصلهٔ ۳۰ روز میان دو تغییر (جلوی ربایش حساب با ربودن یک کانال) — قابل تنظیم.
- **بازنشانی گذرواژه:** این حساب‌ها گذرواژهٔ تصادفی دارند و کاربر هرگز آن را نمی‌داند. فرم `lostpassword` وردپرس با ایمیل واقعی **یک مسیر ورود با گذرواژه برای مشترک** می‌سازد و کانال سوم احراز هویت می‌شود. [پیشنهاد] `allow_password_reset` برای کاربری که `may_use_otp` دارد `false` — فقط مدیران/سردبیران بازنشانی دارند (پرسش باز ۹).

### ۳-ب پاسخ یکسان (جلوگیری از شمارش حساب)

درخواست `topersia_email_code_send` برای هر ایمیل **با قالب معتبر** همیشه یک پاسخ می‌دهد: `200 {token, expiresIn, message:"اگر نشانی درست باشد، کدی فرستاده شد"}` — چه حساب باشد چه نباشد، چه دارای دسترسی (کد نمی‌فرستیم؛ نامهٔ «از ورود عادی استفاده کنید» می‌فرستیم)، چه ایمیل متعلق به حساب دیگر در جریان پیوند. تفاوت‌های **مجاز**: قالب نامعتبر ۴۲۲؛ سقف نرخ ۴۲۹ (برای همهٔ نشانی‌ها یکسان). `token` همیشه ساخته می‌شود (حتی بی نامه)، و برای نشانی بی ارسال هم یک transient با هش تصادفی می‌سازد تا بررسی کد زمان یکسان بگیرد. ارسال نامه پس از پاسخ (`register_shutdown_function` + `fastcgi_finish_request` اگر هست، یا رویداد تک‌باره `wp_schedule_single_event`) تا زمان پاسخ حساب‌دار/بی‌حساب یکی باشد.
**اصلاح‌طلبی لازم برای پیامک [کد]:** امروز `send_otp` برای شمارهٔ حساب دارای دسترسی ۴۰۳ «باید از ورود عادی وارد شود» می‌دهد (`auth.php:362-369`) — این **شمارش حساب‌های دارای دسترسی** است. برای کانال ایمیل چنین نباشد؛ برای پیامک هم در فاز بعد همسان شود (پرسش باز ۸).

### ۳-پ قالب نامه

- **متن ساده (`text/plain`) + HTML سبک** (`multipart/alternative`)؛ HTML: یک جدول، CSS درون‌خطی، فاقد تصویر، فاقد پیکسل، **فاقد هر پیوند ردیابی‌شونده** (حتی بازنویسی پیوند توسط سرویس ایمیل باید خاموش باشد: در Brevo/SES/Postmark گزینهٔ `click tracking`/`open tracking` غیرفعال). تنها پیوند: نشانی سایت به‌صورت متن.
- **محتوا:** عنوان (موضوع) شامل کد نیست (برخی کلاینت‌ها در پیش‌نمایش لاک‌اسکرین نشان می‌دهند — [پیشنهاد] موضوع ثابت بی کد؛ کد در متن)؛ کد درشت؛ عمر ده دقیقه؛ «اگر شما نخواستید نادیده بگیرید؛ کسی به حسابتان دسترسی پیدا نکرده»؛ هشدار «ToPersia هرگز کد را از شما نمی‌خواهد»؛ بدون نام کاربر/شماره.
- **زبان:** زبان صفحهٔ ورود (`ToPersia_I18n::current_language()`، `class-topersia-i18n.php:244`) به درخواست فرستاده می‌شود؛ جهت `dir=rtl/ltr` در HTML. کلیدهای تازه در همان واژه‌نامهٔ سه‌زبانه (`class-topersia-i18n.php:127-159`): `email_*` برای رابط و `mail_code_subject/body/ignore/ttl/footer`. fa · en · ar اکنون؛ **گسترش به ۹ زبان**: واژه‌نامه `[fa][en][ar]` ثابت است — افزودن زبان = کلید تازه در هر ردیف + `current_language()` + `wpml_translate_single_string` (پیش‌تر برای ترجمه با WPML آماده است، `i18n.php:279-290`). قالب‌ها در `templates/email/code.php` و `code.txt.php` متن را از `ToPersia_I18n::in($key,$lang)` می‌گیرند تا افزودن زبان نیاز به کد نداشته باشد. اعداد کد **لاتین** (نامه با کلاینت‌های RTL و کپی‌کردن سازگارتر است)؛ در تحقیق دسترس‌پذیری، کد با `<span dir="ltr">` .
- **سربرگ‌ها:** `From: ToPersia <no-reply@topersia.com>`، `Reply-To` ندارد (یا صندوق پشتیبانی)، `Auto-Submitted: auto-generated`، `X-Auto-Response-Suppress: All`، `List-Unsubscribe` **نه** (نامهٔ تراکنشی). `Message-ID` از دامنهٔ خودمان.

## ۴ — سرویس ایمیل تراکنشی (مقایسه)

> **هشدار روش:** جست‌وجو در دسترس بود؛ دریافت صفحه‌های اصلی شرایط (WebFetch) در این محیط ممکن نشد (`getaddrinfo ENOTFOUND`). پس متن ToS **عینی از منبع اصلی** نقل نشده؛ هرچه از گزارش ثانویه آمده «[تأییدنشده]» است. قیمت‌ها از صفحه‌های تجمیع‌کنندهٔ شخص ثالث‌اند مگر جایی که نوشته شده. **هیچ ثبت‌نامی انجام نشد.**
> **درباره تحریم:** حتی اگر فرستنده «از طرف مالک ایرانی» باشد، ثبت‌نام با هویت/نشانی/کارت غیرواقعی یا با VPN برای پنهان‌کردن محل، ToS را می‌شکند و ریسک بستن حساب (و قطع ناگهانی ورود کاربران) دارد؛ این سند چنین کاری را پیشنهاد نمی‌کند. پاسخ قطعی = مشاور حقوقی/پشتیبانی هر سرویس **کتبی** (پرسش باز ۱).

## ۵ — DNS: فهرست کار مالک

نشانی فرستنده: `no-reply@topersia.com` [پیشنهاد؛ پرسش ۳]. زیردامنه جدا برای تراکنشی (`mail.topersia.com` یا `auth.topersia.com`) اعتبار دامنهٔ اصلی را از خطای بازاریابی آینده جدا می‌کند — [پیشنهاد] برای `From` همان دامنهٔ اصلی بماند و فقط `Return-Path`/DKIM selector زیردامنه‌ای شود (سرویس‌ها خودشان می‌گویند).

- [ ] **SPF:** یک رکورد TXT روی `topersia.com` (فقط **یک** SPF!): `v=spf1 include:<فروشنده> ~all` (در آغاز `~all`، پس از دو هفته پایش `-all`). اگر میزبان SMTP است، IP/`include:` میزبان. اگر دامنه ایمیل دیگری هم دارد، ادغام در همان یک رکورد.
- [ ] **DKIM:** رکوردهای CNAME/TXT که فروشنده می‌دهد (`selector._domainkey`). کلید ۲۰۴۸ بیت. پس از ساخت، «Verified» در پنل.
- [ ] **DMARC:** TXT روی `_dmarc.topersia.com`: شروع `v=DMARC1; p=none; rua=mailto:dmarc@topersia.com; adkim=s; aspf=s;`، دو تا چهار هفته گزارش، سپس `p=quarantine`، بعد `p=reject`. صندوق دریافت گزارش واقعی لازم است (یا سرویس رایگان گزارش‌خوان).
- [ ] **همترازی (alignment):** `From` باید با دامنهٔ DKIM/Return-Path همتراز باشد وگرنه DMARC می‌افتد.
- [ ] **rDNS / HELO** (فقط SMTP میزبان): PTR IP به نام میزبان، HELO هماهنگ.
- [ ] **MX و صندوق:** `no-reply@` لازم نیست صندوق داشته باشد ولی **`abuse@`، `postmaster@`، `dmarc@`** (و یک صندوق پشتیبانی برای `Reply-To`) لازم‌اند.
- [ ] **دامنهٔ ساختگی `users.topersia.com`:** Null MX (`MX 0 .`) + `v=spf1 -all` (§۱-ث). [تأییدنشده] وضعیت فعلی.
- [ ] **MTA-STS / TLS-RPT / BIMI:** اختیاری، پس از DMARC=reject.
- [ ] **پیش‌گرم‌کردن (warm-up):** IP/دامنهٔ تازه با حجم کم شروع شود؛ روز اول فقط ایمیل‌های خود مالک و آزمون به Gmail/Outlook/Yahoo.
- [ ] **آزمون:** mail-tester.com یا ارسال به Gmail و «Show original» (SPF/DKIM/DMARC همه PASS) پیش از روشن‌کردن فرم.
- [ ] **ثبت در Google Postmaster Tools و Microsoft SNDS** برای دامنه.

### ۶-الف دو گزینه و پیش‌فرض

- `type=email`, `autocomplete="email"` و برای کد `autocomplete="one-time-code"`, `inputmode="numeric"`, `pattern="[0-9]{6}"` (موجود، `login.php:30`)؛ برچسب `<label for>` واقعی؛ `aria-live=polite` برای پیام (موجود `login.php:33`) و `role=alert` برای خطا.

- ورودی ایمیل: `dir=ltr` حتی در صفحه RTL (مثل `placeholder` شماره `login.php:27`).

### ۶-پ کش صفحه و نانس

مسئله [کد/سند]: HTML مهمان `ToPersiaUserCore.nonce` را دارد (`assets.php:49`)؛ نانس مهمان ۱۲–۲۴ ساعت معتبر است و صفحهٔ کش‌شدهٔ قدیمی‌تر ۴۰۳ می‌دهد؛ راه‌حل فعلی = TTL کش < ۱۲ ساعت (`LAUNCH.md` H-1 بند ۲، P5-D372).
**فرض این سند:** «دستهٔ ۱۸» (آینده) نانس مهمان را از HTML کش‌شده برمی‌دارد. [تأییدنشده] آخرین دسته در مخزن ۱۶ است (`git log`، `cfd7c73a`)؛ متن دستهٔ ۱۸ در مخزن نیست.
**پیشنهاد — فرم ورود نانس را بر حسب نیاز بگیرد:**
۱. هنگام **باز شدن** پنجره/فوکوس روی فیلد (نه در بارگذاری صفحه، تا فرم‌های بی استفاده درخواست نزنند) JS یک `POST admin-ajax.php?action=topersia_login_token` می‌فرستد.
۲. پاسخ: `{token}` که **توکن بی‌حالت (stateless) امضاشده** است: `base64url(ts|rand).HMAC-SHA256(wp_salt('nonce'), ts|rand|host)`؛ عمر ۳۰ دقیقه، همراه `Cache-Control: no-store` و `nocache_headers()` + `litespeed_control_set_nocache` (POST معمولاً کش نمی‌شود، ولی صریح بنویس) + بیرون از کش صفحه (`topersia_pagecache_nocache`، `P5-D372`).
۳. درخواست‌های `send`/`verify` توکن را در سرآیند `X-TP-Login-Token` می‌فرستند؛ سرور HMAC و عمر را می‌سنجد، **و** `Origin`/`Sec-Fetch-Site` اگر هست باید همین میزبان باشد (`wp_validate_redirect`-مانند برای میزبان).
۴. پاسخ AJAX از دامنهٔ دیگر خوانده نمی‌شود (CORS بسته)، پس صفحهٔ مهاجم توکن نمی‌گیرد؛ این **CSRF ورود** (login-CSRF) را می‌بندد که نانس مهمان (برای همه یکسان در ۱۲ ساعت) نمی‌بست.
۵. اگر دستهٔ ۱۸ هنوز نیامده بود، فرم همین مسیر را دارد و `ToPersiaUserCore.nonce` برای کنش‌های **واردشده** می‌ماند (آن‌ها از HTML واردشده می‌آیند که کش نمی‌شود، `LAUNCH.md` فهرست شاهد).
مسیر موبایلی هم باید به همین توکن منتقل شود تا دو مسیر دو سیاست نداشته باشند (`auth.php:120-124` ← `token_ok()`).

## ۹ — نقطهٔ گسترش (تلگرام Gateway و Passkey) — بی پیاده‌سازی

امروز `send_otp()` مستقیم `new ToPersia_Mediana_SMS` می‌سازد (`auth.php:381`) و `verify_otp` فرض «شمارهٔ موبایل» دارد (`:475`). برای افزودن کانال بدون بازنویسی:

```php
interface ToPersia_Auth_Channel {
    public function id(): string;                       // 'sms' | 'email' | 'telegram_gateway' | 'passkey'
    public function normalize( string $raw ): ?string;  // شناسهٔ نرمال یا null
    public function lookup( string $ident ): ?WP_User;  // _topersia_mobile | user_email | …
    public function attach( WP_User $u, string $ident ): bool;  // پیوند پس از ورود (§۲-پ)
    public function challenge( string $ident, string $lang, array $ctx ): array; // ارسال و/یا گرفتن چالش (OTP: کد؛ Passkey: challenge WebAuthn)
    public function verify( array $stored, array $input ): bool;                 // مقایسهٔ ثابت‌زمان
    public function limits(): array;                    // سقف‌ها، TTL، cooldown
    public function label( string $lang ): string;      // رشتهٔ رابط
}
```

- **ثبت:** `ToPersia_Auth_Channels::register(…)`؛ صافی `topersia_auth_channels`؛ رابط زبانه‌ها از فهرست ثبت‌شده ساخته می‌شود (§۶-الف).
- **منطق مشترک می‌ماند در `ToPersia_Auth`:** توکن، سقف‌های سه‌لایه (پارامتر از `limits()`)، `may_use_otp`، لاگ، `safe_redirect`، ساخت نشست.
- **تلگرام Gateway:** سرویس ارسال کد تأیید از طریق تلگرام برای شمارهٔ موبایل (`sendVerificationMessage`/`checkVerificationStatus`؛ [تأییدنشده: API و قیمت در این جلسه جست‌وجو نشد]) — همان شناسهٔ «موبایل» با کانال تحویل دیگر؛ پس کانال `sms` را با `delivery` گسترش می‌دهد نه شناسهٔ جدید (P5-D377: پس از ایمیل). کلید و رمز با P5-D249.
- **Passkey (WebAuthn):** شناسه = اعتبارنامهٔ عمومی (جدول/متا لازم: `credential_id`, `public_key`, `sign_count`) ← **تنها کانالی که ذخیره‌سازی تازه می‌خواهد** (user meta آرایه‌ای یا جدول)؛ `challenge()` چالش تصادفی می‌سازد و `verify()` امضا را می‌سنجد؛ فقط **پس از ورود** افزودنی (مثل شناسهٔ دوم) و به‌عنوان «ورود سریع»، نه جایگزین بازیابی. نیازمند HTTPS و `rp.id=topersia.com`. [تأییدنشده: کتابخانهٔ PHP مناسب و سازگاری PHP 8.0].
- **واتساپ: نه** (تصمیم مالک).
- **نگه‌داشتن سازگاری:** نام کنش‌های AJAX فعلی (`topersia_send_otp`/`topersia_verify_otp`) بماند (JS و هستهٔ نمایش به آن‌ها وصل‌اند، `UC/CLAUDE.md` «API برای هستهٔ نمایش»)؛ کنش‌های تازه `topersia_email_code_send/verify` و در فاز دوم بازنویسی به یک جفت عمومی `topersia_auth_challenge/verify` با پارامتر `channel`، و کنش‌های قدیمی لفاف روی آن.
